# 下单收货校验与订单删除（T063）

## 用户操作

秒杀前在“收货地址”填写收货人、联系电话、完整地址。在商品页点击“立即抢购”，选择收货地址，再完成验证码和提交。没有地址时抢购提交按钮禁用；可通过弹窗中的“管理收货地址”进入填写页面。

服务端在抢购前保存收货快照；异步订单创建时在同一事务写入订单和履约收货信息。以后删除地址簿不会删掉本单收货快照。已存在的历史订单不会被批量改写。

“我的订单”及“秒杀收货”页面中：

| 状态 | 操作 |
| --- | --- |
| 待支付 | 先“取消订单”，关闭与库存回补仍走原幂等流程；真实微信意图须先确认渠道关闭 |
| 已支付未发货 | 先退款；模拟退款和真实微信退款沿用各自原流程 |
| 待收货 | 不能直接删除，先完成履约 |
| 已取消 / 已退款 / 已完成 | 显示“删除订单”，确认后从本人的订单列表移除 |

删除不会物理删除订单、支付凭证、履约或库存记录，也不会再回补一次库存。管理员仍可核查历史交易；原深链接/请求查询保留交易事实。删除不是取消订单、退款或清空数据库的替代操作。

## API契约

| 接口 | 输入 / 返回 | 保护 |
| --- | --- | --- |
| `POST /api/shop/seckill/checkout` | 严格body：activityId、skuId、requestId(UUID)、addressId；返回requestId、status=READY | 本人完整地址；地址/活动存在；相同请求相同地址幂等，不同地址409 CHECKOUT_CONFLICT；非本人地址404 ADDRESS_NOT_FOUND |
| `POST /api/seckill/buy` | 原字段不变，须先准备上述收货快照 | 新请求无入场标记返回409 ADDRESS_REQUIRED，预扣/证明消费之前拒绝；原请求重放仍返回原事实 |
| `POST /api/shop/seckill/{id}/cancel` | 空对象，返回orderId、status=CLOSED | 仅本人待支付；关闭重试幂等；已付款409；真实微信未确认关闭409 WECHAT_CLOSE_REQUIRED |
| `DELETE /api/shop/orders/{id}` | 无body，返回orderId、status=DELETED | 普通订单，仅本人允许终态；重复删除200 |
| `DELETE /api/shop/seckill/{id}` | 同上 | 秒杀订单，合并退款/履约终态；保留原PAID库存事实 |

ID、金额和时间采用项目原有字符串口径。所有接口须Bearer认证；越权和不存在统一404；未认证401；非允许删除状态409 ORDER_DELETE_NOT_ALLOWED。所有列表仅过滤本人删除标记，管理列表保留。

## 一致性和升级

`010_seckill_checkout_delete.sql`新增不可变收货准备记录与逻辑删除记录；不改旧迁移。Java先事务提交SQL快照，再写24小时Redis入场标记（仅“1”，绑定用户/活动/SKU/requestId，不含收货隐私）；写失败沿用相同请求重试。C++新请求在预扣前检查标记，消费者最终读取SQL快照，缺失时写持久补偿，不生成订单。MQ事件契约不变，无收货人/电话/地址。

SQL快照和Redis不是一个事务：SQL提交、标记未成功时不能入场，可重试；标记丢失先重试prepare；标记存在但SQL缺失时消费者补偿。订单及履约快照在同一SQL事务提交。地址快照不会随地址簿删除而变更。

订单删除事务先验本人，再锁订单并复查当前终态；`order_deletions`唯一键保证重放幂等。取消沿用库存父行→订单锁序与原回补outbox，支付与取消只能一方成功。

部署先构建源码镜像、执行增量迁移，再更新Java/C++/relay/前端；旧客户端须刷新后再提交新抢购，不能继续跳过prepare。已有容量报告是旧版本证据；新增收货准备/入场查询后未重新做30分钟容量验收，不能复用旧性能结论。

## 单笔历史演示数据维护

本次唯一缺收货信息的旧模拟支付订单由用户明确要求删除。维护脚本`scripts/repair-missing-shipping-demo.py`默认只读预览；显式`--apply`才退款并逻辑删除。必须指定准确订单UUID；只允许没有履约记录、没有真实微信意图、PAID且MOCK成功的订单，正常订单拒绝。锁序、金额、唯一退款凭证与原MOCK退款一致，不恢复已支付秒杀库存或资格。不要将此脚本用于真实支付或批量清理。
