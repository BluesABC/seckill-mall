# S19 / T052 混合旅程与突发测试计划

状态：工况与程序门槛已固定，实测结论以PROGRESS和阶段验收报告为准。关联G02/G04/G09/G10/G11，继续采用v0.1小规模假设。本文件整理工况，不将暂定目标改写成生产承诺。

## 固定工况

| 项目 | 值与口径 |
| --- | --- |
| 平台 | 自有S7 Compose保留卷、WSL原生Python3、同机Docker，12逻辑CPU/约8GB；原有历史订单继续正常处理 |
| 业务配置 | C++32线程/128排队、4消费线程/4个MQ队列；与S17对照；退出恢复进入测试前的线程/队列 |
| 背景浏览 | 15请求/秒×1800秒，共27,000次GET；列表、筛选列表、详情、活动信息、订单列表、当前身份六族轮换 |
| 完整旅程 | 64条均匀插入30分钟，三场活动，每场64库存；背景读之外另统计其实际HTTP调用，不能称为15条旅程/秒 |
| 账号 | 8次真实注册在计时内；另56个预置账号复用一次真实注册得到的bcrypt哈希，64个全部走真实登录，不写入会话夹具 |
| 登录/注册频控 | Java每来源IP登录80次/10分钟、注册15次/10分钟保持原样；一条旅程仅一次登录，不能用改变限流解释通过 |
| 验证码/令牌 | 各32次图片与可读题面请求；图片真实生成并验证PNG，仅隔离夹具改答案摘要且KEEPTTL；可读题按题面求解；真实token兑换，证明仍60秒 |
| 重复提交 | 每8条旅程重放一次相同buy/requestId，共8次，必须同reservationId，不得换ID重抢 |
| 支付与自然关闭 | 前16条不支付，原900000ms期限自然关闭；其余48条MOCK支付，每条同幂等键重放一次；SQL应有48条唯一支付 |
| 关闭观察 | 背景订单列表轮换所有已登录账号，观察CLOSED；记录客户端monotonic时间，按MySQL时钟探针估算到期基准；包含轮询开销，P99暂定≤60秒 |
| 数据核对 | 64请求/64唯一reservation与活动用户资格；48 PAID+16 CLOSED；每场初始64=可售48+有效占用16，三场均只读CLEAN，无pending/outbox/MQ失败 |
| 突发一 | 64账号经真实可读验证码/token预备后同时buy，库存64；必须64受理/64订单，随后MOCK支付和CLEAN |
| 突发二 | 相同64账号在新活动同时buy，库存32；必须32受理/32订单和32次SOLD_OUT，5xx/429/未知传输不得当作售罄；支付后CLEAN |

突发测的是64人同步提交的库存正确性，报告HTTP延迟；凭据准备不与同时提交混算。结果逐个查询时的订单观察延迟是保守上界，不作为突发落库延迟门禁，也不据瞬时吞吐推导持续QPS。

## 延迟和错误门槛

| 接口族 | 暂定P95目标ms | 依据 |
| --- | ---: | --- |
| 商品列表/筛选列表 | 500 | v0.1列表API |
| 商品详情 | 300 | v0.1详情API |
| 活动信息/验证码/token/buy及buy重放 | 500 | 下单响应目标与本专项工程预算；非生产SLA |
| 当前身份/订单列表/状态轮询 | 1000 | v0.1一般读API默认值 |
| 注册/登录/MOCK支付及重放 | 1000 | 小规模工程验证预算；尚无渠道SLA |
| 请求到订单可查 | P95≤3000、P99≤8000 | v0.1异步下单目标，采用同机monotonic请求到真实查询看到订单的时间 |

所有接口同时报告P50/P95/P99与状态计数，不能排除超时样本。合格流程本专项要求无意外4xx/5xx/未知传输，重放和售罄各自列出。背景读完成27,000次、测得发流时长覆盖1800秒（允许一个调度间隔误差），有效发送率不得低于目标99%。
