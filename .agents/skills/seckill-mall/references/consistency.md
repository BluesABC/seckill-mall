# 一致性与可靠性约束

这些约束是对原文防超卖、幂等和最终一致性目标的工程细化。实现可选择具体机制，但必须说明机制覆盖的失败窗口和恢复路径。

## 库存与资格

- 活动开始前从持久化库存生成活动库存快照，并记录活动版本；活动运行中不得直接覆盖 Redis 预扣库存。商品/SKU 库存和活动分配库存的关系须明确，不能独立重复售卖同一份库存。
- Lua 一次原子检查活动有效性、余量、购买资格，再写预扣、资格和请求状态。库存不足或资格不满足时无部分副作用。价格、用户身份和活动时间以服务端为准。
- 请求 ID 支持重复请求返回同一业务结果；活动/商品/用户资格另有业务唯一性约束。两者不能互相替代。
- Redis Key 包含活动与商品维度，例如 `seckill:{activityId:skuId}:stock`、`...:user:<userId>`、`...:request:<requestId>`。使用 Redis Cluster 时，同一 Lua 访问的所有 Key 必须同槽；上述括号标签仅为示例，需评估热点与数据规模。
- 资格/预扣记录的 TTL 不可早于消息重试、下单恢复和对账窗口。缓存丢失或过期后应以持久化数据恢复，不能直接把用户重新当作首次购买。
- MySQL 在同一事务内完成幂等约束、库存条件扣减、订单创建与必要事件落盘。条件更新影响行数必须恰为 1；重复订单或失败不得额外扣库存。针对唯一键冲突要读取并校验已有业务结果。

## Redis 预扣与消息投递

Redis 操作和外部 MQ 投递不能当作一个原子事务。必须覆盖“预扣后进程崩溃”“发送成功但确认丢失”“确认前 MQ 崩溃”“重试重复投递”等窗口。

实现可恢复请求/投递记录：当前单ledger Hash原子写预扣与pending事件，转发器投递用户选择的RocketMQ。明确持久性、Redis故障边界、扫描恢复和对账补偿；如果未来引入Redis Stream作待投递记录，也不能代替当前RocketMQ主削峰链路。

- 投递状态未知时按请求 ID 查询或幂等重试，不能立即回补而让已经创建的订单继续占用库存。
- “已受理”响应的可靠性边界必须写入 API 契约；客户端超时不代表请求失败，按请求 ID 查询。
- 当前RocketMQ明确Broker刷盘/复制配置、生产确认、消费者ACK、重投、顺序与故障恢复语义；单Broker开发环境不可标为HA。未来切自研C++ MQ仍保持同样验收要求。
- 主业务采用至少一次投递与幂等消费，不宣称未经证实的端到端 exactly-once。订单事务提交后才 ACK；提交后 ACK 丢失导致的重投须安全。
- 消息包含 schemaVersion、eventId、requestId、activityId、skuId、userId、quantity、reservationId、服务端价格快照及时间/追踪信息；定义跨语言序列化、兼容与校验规则。
- 重试退避、次数上限、死信持久化、告警和人工/自动重放均需可观察。重放保留原业务幂等标识，不能通过换 ID 绕过唯一约束。

## 状态机与回补

定义预扣、待投递、排队、待支付、已支付、关闭/失败和补偿状态；区分请求受理记录与订单状态，避免把消息 ACK 等同于支付成功。

- 支付与超时关闭通过数据库状态条件更新/事务竞争同一个待支付状态，只有一方成功。已支付订单不可被延迟关闭消息回补。
- 支付入口校验订单归属、金额与支付凭证；真实支付回调验签并幂等。超时关闭后的迟到支付应进入明确的退款/人工处理流程，不能静默改回已支付。
- 每次关闭或下单终止产生可恢复且唯一的回补事件。DB 状态、DB 库存和事件记录事务一致；Redis 回补幂等，故障恢复后只执行一次。
- DB 尚未扣库存的预扣失败只释放相应 Redis 预留；已创建订单关闭则释放 DB 和 Redis 相应资源，不能统一盲加两层库存。
- Redis 回补与资格状态变更需原子校验 reservationId/版本，不能误删同一用户后来生成的新资格。
- 支付后的订单保留永久购买事实；是否允许取消后重抢由明确业务规则控制。

## 对账与降级

- 用明确统计口径建库存守恒账：活动初始库存 = 可售库存 + 在途预留 + 未支付订单占用 + 已支付占用；取消与补偿归还可售项。实际状态和时间窗口需去重，不能把 MQ 消息数直接当作订单数。
- Redis 与 DB 短时不相等是异步链路的可能状态；对账要考虑排队、重试、事务提交与读取快照时间，识别超出约定收敛窗口的异常。
- 消息积压、Redis 故障或 DB 饱和时使用有界队列、消费并发限制、背压与拒绝/降级；不能无限缓存，也不能绕过库存校验直写订单。
- 所有补偿可追踪、有幂等键和审计记录。不要用清空缓存或强制覆盖运行中库存作为自动修复。
