# S17 / T050 持续容量修复验收

- 日期：2026-10-17；需求：G02/G04/G09/G10/G11。
- 结论：**本机15 QPS×30分钟下单创建专项门禁通过**。原有S16失败报告保留。
- 负载：单热点SKU、27,000个合格唯一请求、初始库存27,000；真实Nginx→C++→Redis Lua/AOF→RocketMQ→Java→MySQL→outbox链路。
- 环境：WSL2 Ubuntu、Docker Desktop，12逻辑CPU/约8GB共享资源、DrvFs；压测器与服务同宿主机。32个C++线程/128排队任务、4个消费者线程、4个MQ队列。镜像ID、源码哈希及发流前保留数据规模见原始报告。

## 本次修复

1. 活动元数据读取由HGETALL改为固定9字段HMGET。57,761字段账本的20次查询期间Redis输出由143,399,588 B降为5,128 B（全局计数包含后台流量），避免随活动历史增长的读取放大。
2. cpp-httplib后端每连接一次响应并关闭，释放被Nginx空闲连接占用的同步工作线程；浏览器到Nginx仍可复用连接。
3. 新预扣已明确写入时保留同连接WAITAOF、省去多余确认写入；只读重放仍写causal fence。Java一次HMGET读取四项原始凭据，outbox用索引join锁定事件与请求。
4. Relay非空成功轮次立即再扫；空轮次和失败才等待。outbox独立于过期关闭/恢复扫描调度，保留逐事件事务、锁内PENDING重查、Redis持久化确认和有界关闭。
5. Java原Lua与因果持久化标记合并到同次EVAL，保留原参数校验/返回与同连接WAITAOF；只读重放仍写标记。独立派发后的6分钟诊断仍积压1,226条，因此继续修复，不将中间结果计为通过。
6. 用户初始化、首批证明预备和环境探针移到发送时钟之前，避免初始化补发突发；HTTP202、全部响应、数据库持久化和库存守恒分别核对。
