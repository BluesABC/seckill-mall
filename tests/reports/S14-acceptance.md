# S14 验收：C++ HTTP 工作线程扫描

日期：2026-10-14（V019）。目标是辨别 C++ 入口工作线程是否是热点秒杀延迟的主要限制，并确认改变并发度后交易守恒。此阶段完成了扫描，不代表性能门禁达标。

## 环境与方法

- WSL2 Ubuntu 24.04.4，Docker 29.8.2 / Compose 5.6.0；12逻辑CPU、约8GB Docker预算。使用项目专属 `seckill-mall-s7` 栈和既有卷，未删除/重置业务卷。
- 工作线程8/16/24/32/48/64，每档3轮；每轮64个用户并发争抢一个库存64的热点SKU。请求走真实HTTP→Redis→RocketMQ→Java→MySQL。
- 每档启动前检查运行中C++容器的 `MALL_HTTP_WORKERS`，不匹配即停止；脚本退出时恢复默认8。HTTP使用单调时钟计时，MySQL创建时间按每轮测得的WSL/容器时钟偏差校正。
- 每轮验收64个请求受理、64个订单可查、只读库存对账CLEAN；共18/18轮通过。原始数据按工作线程数保存在本目录的 `wsl/s14-workers-*.json`。

## 结果

| C++工作线程 | 突发受理QPS中位数 | HTTP P95中位数 | 订单可查P95中位数 | 对账 |
| ---: | ---: | ---: | ---: | --- |
| 8 | 4.25 | 14,593 ms | 13,048 ms | CLEAN 3/3 |
| 16 | 8.46 | 6,441 ms | 7,499 ms | CLEAN 3/3 |
| 24 | 14.26 | 4,406 ms | 5,610 ms | CLEAN 3/3 |
| 32 | 23.97 | 2,281 ms | 4,272 ms | CLEAN 3/3 |
| 48 | 27.38 | 2,302 ms | 3,155 ms | CLEAN 3/3 |
| 64 | 56.87 | 186 ms | 3,525 ms | CLEAN 3/3 |

QPS仅代表64个请求集中提交的短突发吞吐，不可外推为持续QPS；入口突发窗口很短时该数值会升高。增大线程数显著降低了入口P95；32/48/64线程订单可查P95中位数为4.272/3.155/3.525秒，均超过v0.1的3秒暂定目标。64线程并未优于48线程。正确性与库存守恒在全部轮次通过。

## 阶段结论与限制

- C++入口排队是可改善的一段，但不是唯一或当前剩余订单延迟的充分解释。没有分段追踪证据，不能断言瓶颈就是Broker、relay或MySQL锁。
- 暂时保留通用Compose默认8线程；48线程仅作为本机12逻辑CPU下后续诊断候选。不得作为生产规格建议。
- v0.1的15 QPS连续30分钟目标和订单延迟门禁尚未完成；该测试同机压测、样本小、非生产拓扑，不能证明容量、SLA或HA。

复现：`bash scripts/test-s14-wsl.sh`。脚本要求已有自有S7配置和卷，失败时保留证据且不会清理卷。
